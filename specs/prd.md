# 产品需求文档 (PRD)：气球打字（小霸王学习卡《打字游戏》复刻）

## 1. 项目概述

- **项目名称**：Typing Balloon / 气球打字
- **定位**：零后端、零第三方依赖、零资源文件、可直接托管在 GitHub Pages 的
  像素风打字练习应用。
- **核心亮点**：
  - **像素级复刻 FC 原味**：逻辑分辨率固定 256×240（NES 原生），显示只取整数倍，
    `image-rendering: pixelated`；字母是手绘 5×7 点阵字模，汉字用本机字体现场
    二值化成 16×16 的 1bit 点阵块；所有图形走 `fillRect`。
  - **零依赖、零资源文件**：无构建步骤、无 CDN、无图片/字体/音频文件，
    整个应用 < 160 KB 纯文本，首屏加载即全部代码。
  - **音效现场合成**：方波（可调占空比）+ 三角波 + 噪声缓冲，全部 Web Audio
    振荡器，参数集中在 `js/audio.js` 的一张表里。这是系列五个项目中**第一个
    有声音的**。
  - **难度如实标注**：档位参数显式写在 `js/difficulty.js`，菜单与侧栏的文案
    全部由它现生成，不做任何加工。
  - **数据诚实**：侧栏逐条列出每一次击破的**真实反应时间**，并与该气球自身的
    可用时间并排展示；慢于自身可用时间 60% 的行标黄。沿用 04.Gomoku 的诚信原则。

---

## 2. 调研结论（复刻对象考证）

### 2.1 这游戏是什么

**它不是独立发售的游戏**，而是**小霸王「中英文电脑学习卡」内置的《打字游戏》**
（SB-926 等机型标配，位于「指法练习」之后的进阶项目）。所以网上找不到叫
「气球打字」的独立 ROM——它始终是学习卡固件的一部分。

> 这一条是整个调研中最关键的结论：它解释了为什么按"找 ROM"的思路调研会一无所获，
> 也决定了本项目的"还原"必须靠**教材文字 + 玩家记忆 + 实机录像**三方互证，
> 而不是对着某一版 ROM 反汇编。

### 2.2 原版玩法（**每条标注可信度**）

| # | 结论 | 可信度 | 依据 |
|---|---|---|---|
| 1 | 气球上带字符，从**屏幕上方往下降** | **高**（多来源互证） | 教材文字描述 + 多家复刻帖一致 |
| 2 | 按对应按键即击破气球 | **高** | 同上，玩法本身无歧义 |
| 3 | 标志性动画是**一只小鸟飞来把气球啄破** | **高** | 教材描述 + V2EX 复刻者回帖，独立互证 |
| 4 | 难度分 **0～9 级**，级别越大气球落得越快 | 中 | 有来源提及，未做交叉验证 |
| 5 | 失败判定不是生命值，而是**气球落地砸坑 → 地面塌陷** | 中 | 玩家记忆，未做交叉验证 |
| 6 | 结束后统计速度（字/分）、正确率，给「低/中/高」评语 | 中 | 玩家记忆 |
| 7 | 气球往上飘（而非下落） | **存疑** | 与教材文字矛盾，仅个别玩家记忆 |

**第 7 条的处置**：本项目**取下落**。理由是教材文字与多数实机录像一致，
且下落与"砸出弹坑"的失败判定在物理上自洽——往上飘的气球不会砸地。

**没有把握的部分一律标了可信度，不做"看起来像考证"的编造。** 引用来源清单见
仓库根目录的 `NOTICE.md`。

### 2.3 同时期的同类

| 游戏 | 玩法要点 | 与本项目的关系 |
|---|---|---|
| 金山打字通「玩泡泡」 | 泡泡带字，错满 10 个结束 | 失败判定不同（生命值 vs 地形），本项目不采用 |
| Mario Teaches Typing (1991) | 打字推进关卡 | 机制不同，仅作同时期参照 |
| TypingGamesKids Balloon Pop | 气球带字，点破 | 玩法近似，但无地面塌陷 |
| 方竹打字游戏 | 五笔字根气球，从左向右漂 | 方向与输入法均不同，仅作参照 |
| vicalloy/apple-guardian | 苹果掉落 + 打字消灭害虫 | **变形而非复刻**；本项目未复用其任何代码 |

### 2.4 技术路线选型

调研期间确认过若干现成复刻，**全部不采用**，理由如下：

1. `vicalloy/apple-guardian` 用 Phaser + React + Vite——引入框架与构建管线，
   与本系列"纯静态零构建"的约定直接冲突，且它是玩法变形，不是像素级复刻；
2. 原版没有独立 ROM，任何"基于 ROM 还原"的路线都不成立；
3. 本项目要的是**像素观感**而非**低分辨率观感**——这决定了所有图形必须手工
   走 `fillRect`，用现成游戏框架反而要跟它的抗锯齿渲染管线作斗争。

因此自研：原生 Canvas + 手绘点阵字模 + Web Audio 合成，零依赖。

## 3. 技术架构与分层

沿用系列的「**视图 UI — 业务裁判 — 数据/参数**」解耦：

```text
+-------------------------------------------------------------------+
|                       Web UI (视图层)                              |
|  Canvas 256×240 像素渲染 + 侧栏统计 + 多级菜单遮罩 + 模块化 CSS      |
+------------------------------+------------------------------------+
|                    业务裁判层 (主线程)                              |
|  rules.js         生成 / 下落 / 匹配 / 计分 / 地面塌陷 / 结束判定     |
|  difficulty.js    档位与模式的唯一事实来源（经典脚本 → window.Difficulty）|
|  data/words.js    字母 / 单词 / 汉字题库（纯数据，无逻辑）             |
+------------------------------+------------------------------------+
|                       表现层（只消费，不回写）                       |
|  ui/stage.js   Canvas 像素渲染（不判断规则、不推进时间）              |
|  ui/panel.js   侧栏：实时统计 + 逐次击破记录表                       |
|  ui/menu.js    遮罩菜单 / 结算浮层 / toast                          |
|  ui/pixelfont.js  5×7 点阵字模 + 汉字二值化 tile                    |
|  audio.js      Web Audio 合成（只听事件，不看状态）                   |
+-------------------------------------------------------------------+
```

**数据单向流动**：`rules` 产出 `state` + `events`，其余层只消费。反向无通路——
`stage.js` 不能改 `state`，`audio.js` 不能读 `state`。

### 3.1 为什么 `difficulty.js` 是经典脚本而不是 ESM

系列里这么做的原始理由（Worker 的 `importScripts`）在本项目不成立，保留它有两个
实际价值：

1. 档位按钮、模式按钮全部从 `Difficulty.LEVELS` / `Difficulty.MODES` 现生成，
   档位文案与参数**永远同源**；
2. 调参时可以在浏览器 console / playwright 里**直接读 `Difficulty` 做参数扫描**，
   不用翻代码——这是本系列一贯的调参方式（见 `CLAUDE.md` 的校准记录）。

### 3.2 固定步长

逻辑按 **1/60 秒固定步长**推进，渲染跟 `rAF` 走，两者解耦：

- 反应时间、生成间隔、下落速度的测量值与显示刷新率无关（60Hz 与 144Hz 结果一致）；
- 掉帧时最多补 10 步，避免切回标签页时瞬间冲一大截。

### 3.3 像素渲染的三条保证

1. 逻辑分辨率固定 256×240，`canvas.width/height` 就是它，内部无"半像素"；
2. 显示尺寸只取**整数倍**（1x～4x），配合 `image-rendering: pixelated`；
3. 所有图形用 `fillRect` 逐行/逐游程绘制，**禁用 `ctx.arc` / `ctx.ellipse` /
   `shadowBlur`**——这些会抗锯齿。

## 4. 玩法规则

### 4.1 三种模式

| 模式 | id | 气球上是什么 | 输入内容 |
|---|---|---|---|
| 英文字母 | `letters` | 单个字母 A–Z | 该键（大小写均可） |
| 英文单词 | `words` | 一个英文单词 | 完整拼写 |
| 汉字拼音 | `hanzi` | 一个汉字 | 该字的**全拼**（ü 打成 v，不标声调） |

### 4.2 匹配规则（**输入缓冲 + 前缀匹配**，三模式统一）

| 状态 | 行为 |
|---|---|
| 缓冲为空 | 按下的键匹配**以该键开头**的候选气球，取其中 **y 最大（最靠下、最快落地）** 的那个作为当前目标 |
| 缓冲非空 | 只认当前目标，把按键追加到缓冲后继续比对前缀；命中完整目标 → 击破 |
| 不匹配 | 记 1 次失误，缓冲清空，目标进度回退到 0。**不判负** |

**两条硬保证**：

1. **同屏不出现重复目标**（生成时按 `match` 过滤）。否则"按 A 打哪一个 A"
   就是随机事件，玩家会觉得游戏在耍赖。
2. **同屏目标数不超过档位的 `maxBalloons`**；同屏满时不积攒生成计数，
   避免一有空位就连喷几个。

**键盘细节**：监听 `keydown` 的 `e.key`，只认 `/^[a-z0-9]$/`；`ctrlKey`/`metaKey`/
`altKey` 时忽略（不劫持浏览器快捷键）；空格 `preventDefault`（不让页面滚动）。
中文输入法激活时浏览器收不到字母键（`key === 'Process'`），属已知限制，
在「玩法说明」页明确提示切换输入法。

### 4.3 下落时间按目标长度补偿

设档位基准下落秒数为 `fallSec`（单字符），目标字符数为 `len`：

```
实际下落秒数 = fallSec + (len - 1) × PER_CHAR_BONUS_SEC     PER_CHAR_BONUS_SEC = 0.55
```

打一个 9 字母的单词和打一个字母给同样的时间显然不合理。补偿规则统一写在
`difficulty.js` 的 `config(modeId, n, len)` 里，`rules.js` 每次生成气球时按
`state.configFor(picked.match.length)` 现取。

### 4.4 地面塌陷（失败判定）

`ground[16]` 记录 16 列地面各自的**上沿 y 坐标**，初始为 208（地面顶端）。

气球落地时：

```
本列 += 5      相邻列 += 2      隔一列 += 1
```

形成碗形坑。某列上沿达到 **240（画布底）** 时该列**掏穿**；掏穿的列数达到本档的
`collapseLimit` 时本轮结束，弹结算浮层。

**为什么这样设计**：失败条件的每一个中间量都是**屏幕上直接看得见**的——坑在画面
上是实时画出来的，剩余额度在顶部信息条和侧栏各有分段进度条。玩家不会莫名其妙
就输了。

**失误只统计不判负**——与"错满 N 个结束"的同类游戏（金山打字通「玩泡泡」）
刻意区分开。

### 4.5 结算

本轮结束后弹出成绩单：

| 项 | 来源 |
|---|---|
| 模式 / 难度 | `state.mode` / `Difficulty.level()` |
| 用时 | `rules.elapsedMs()` |
| 击破气球数 / 击破字数 | `stats.hits` / `stats.chars` |
| 正确按键 / 失误 | `stats.typed` / `stats.misses` |
| 最高连击 | `stats.bestCombo` |
| 正确率 | `rules.accuracy()` = `typed / (typed + misses)` |
| 速度 | `rules.cpm()` = 每分钟正确字符数 |
| 平均反应 / 最快反应 | `log` 里所有 `ok` 记录的 `reactionMs` |
| 落地漏球 | `stats.landed` |
| 地面塌陷 | `collapsed.length / collapseLimit` |

**评语（低 / 中 / 高）阈值**写在 `js/app.js` 头部常量里，**不是随手拍的比例**：

```js
GRADE_HIGH = { cpm: 180, acc: 0.95 };
GRADE_MID  = { cpm: 90,  acc: 0.88 };
```

速度与正确率两档都要达标才算上一档。

### 4.6 连击

`stats.combo` = **干净的连续击破**：连续击破气球，中间没有失误、也没有漏球。

- 击破一个气球 `+1`，并刷新 `stats.bestCombo`；
- 按错键（`miss`）清零；
- 气球落地（`land`）也清零——漏球和打错一样，都算这一轮"手不顺"。

连击是纯统计量，**不参与任何难度参数**（不改下落速度、不叠分数倍率）。
它唯一的作用是两点反馈：从第 2 连击起叠一个逐级升高的 `combo` 音效，
以及成绩单里的「最高连击」一行。

### 5.1 十档参数表

| 档 | 名称 | fallSec | spawnMs | maxBalloons | collapseLimit | letters | wordTier | hanziTier |
|:--:|:--:|--:|--:|:--:|:--:|:--:|:--:|:--:|
| 0 | 入门 | 9.0 | 1500 | 3 | 6 | 8 | 0 | 0 |
| 1 | 新手 | 8.3 | 1380 | 3 | 6 | 10 | 0 | 0 |
| 2 | 初学 | 7.6 | 1260 | 4 | 5 | 12 | 0 | 1 |
| 3 | 熟练 | 6.9 | 1140 | 4 | 5 | 16 | 1 | 1 |
| 4 | 上手 | 6.2 | 1020 | 5 | 5 | 20 | 1 | 2 |
| 5 | 进阶 | 5.5 | 900 | 5 | 4 | 24 | 1 | 2 |
| 6 | 快速 | 4.8 | 780 | 6 | 4 | 26 | 2 | 2 |
| 7 | 高手 | 4.1 | 660 | 6 | 4 | 26 | 2 | 3 |
| 8 | 精英 | 3.4 | 540 | 7 | 3 | 26 | 3 | 3 |
| 9 | 大师 | 2.7 | 420 | 8 | 3 | 26 | 3 | 3 |

**跨档规则**：

- `PER_CHAR_BONUS_SEC = 0.55` — 目标每多 1 字符补偿的下落秒数；
- `MODE_SPAWN_SCALE = { letters: 1.0, words: 1.3, hanzi: 1.3 }` — 单词/汉字模式的
  生成间隔倍率（目标更长、球出得越稀）。

**首版参数按「完全不操作还能撑多久」反推**（一屏 16 列，每列约能挨 6 下）：
L0 ≈ 39s、L5 ≈ 15s、L9 ≈ 5s。给了最低限度的操作压力，同时不至于一上手就输。

### 5.2 档位的含义与系列的差异

02/03 的难度旋钮映射到**引擎搜索的弱化**（AI 有多强），04 映射到**搜索深度 +
根节点采样**。本项目没有 AI 对手，难度是纯粹的**环境压力**：球落多快、出多密、
地面能挨几下。

玩家的水平**不需要被模拟，只需要被测量**——测量结果进侧栏的统计表。

## 6. 题库

`js/data/words.js` 是**纯数据文件**，没有任何逻辑分支。

| 表 | 规模 | 说明 |
|---|---|---|
| `LETTERS` | 26 | 按英文词频从高到低排列（`etaoinshrdlucmfwygpbvkxjqz`），低档只取前 N 个 |
| `WORDS` | 1342（无重复） | 小写英文单词，长度 3～10+ |
| `HANZI` | 275（无重复） | `{c, p}` 汉字 + 全拼小写，ü→v；172 个不同拼音 |

### 6.1 分桶按长度现算，不手写档位标注

```
WORD_TIER_RANGE  = [[3,4],[5,6],[7,8],[9,∞]]
HANZI_TIER_RANGE = [[0,2],[3,3],[4,4],[5,∞]]     // 按拼音长度
```

落桶结果：wordTier 0→245 词、1→756、2→308、3→33；hanziTier 0→81、1→105、
2→62、3→27。

**为什么不在数据里手写 tier 字段**：手写的标注一旦和实际长度对不上，就是一个
**不会报错的隐性 bug**。分桶规则只有一个地方可查（`bucket()`），且某档为空时
会向相邻档扩散着借，保证返回的数组永远非空——上层不用做空判断。

### 6.2 汉字拼音约定

用**标准全拼小写**，`ü` 一律写成 `v`（女 `nv`、绿 `lv`）——这是中文输入法实际要敲
的键，玩家按的就是这些字母。不标声调：练的是指法，不是拼音。

## 7. 音效

`js/audio.js` 用 Web Audio API 现场合成，**零音频文件**。FC 的 APU 本来就只有
方波、三角波、噪声三种源，用振荡器现场合成比采样更"对味"，且音高、滑音、包络
全是参数，想改就改。

| 音效 | 触发 | 构成 |
|---|---|---|
| `pop` | 击破气球 | 噪声爆裂（3200→600Hz 低通扫频）+ 方波 1400→320Hz 急降 |
| `key` | 一个字符按对（目标未打完） | 方波 1180→880Hz 极短"哒"，音量刻意压低 |
| `combo` | 从第 2 连击起，与 `pop` 同响 | 两音方波点缀，音高随连击数**逐级上升**（见下） |
| `miss` | 按错键 | 两声低音方波短哔（196→165、147→123Hz） |
| `spawn` | 新气球生成 | 噪声上滑 whoosh + 三角波 320→620Hz |
| `land` | 气球落地 | 噪声闷响 + 极低频三角波 |
| `collapse` | 一列塌陷 | 长下降方波 + 长噪声 + 三角波，比落地重得多 |
| `uiMove` | 菜单切页 / 选中 / 关浮层 | 单声方波短音（740Hz） |
| `start` | 开局 | 上行两音（523 / 784Hz），游戏机"叮咚" |
| `over` | 结束 | 下行琶音（784/659/523/392 → 196Hz 三角波） |

**变调**：`play(name, {semitones})` 把整条配方（含噪声层的低通扫频）一起移调，
`combo` 音靠它爬音阶——第 2 连击音高不动，之后每连一个抬一个半音，封顶一个八度
（`Math.min(combo - 2, 12)`）。这样"打得顺"能直接听出来，而不用盯着计数器。

**技术要点**：

- **惰性建上下文**：浏览器自动播放策略要求 `AudioContext` 必须在用户手势里创建
  或 `resume`，所以第一次真正出声前什么都不建，由 `app.js` 在第一次
  `keydown`/`pointerdown` 时调 `unlock()`；
- **占空比**：用 `createPeriodicWave` 按傅里叶系数构造矩形波，逼近 NES 脉冲通道的
  12.5% / 25% / 50% 三种占空比（`setPeriodicWave` 结果按占空比缓存）；
- **确定性噪声**：噪声缓冲用 LCG 生成而不是 `Math.random`，保证每次运行一致；
- **静音 = 不排音**：`play()` 第一行就返回，不往时间轴上堆振荡器节点（自动化驱动
  必须走这条路径，见 `?mute=1`）。

## 8. 界面

沿用系列的视觉骨架（顶部标题栏 / 双栏主区 / 结算浮层 / 底部说明），针对像素画面
定制。详见 [`ui.md`](ui.md)。

**侧栏三张卡**：

1. **本轮信息** — 模式 / 难度 / 用时 / 击破 / 失误 / 正确率 / 速度 + 塌陷进度条 +
   重开/菜单/静音按钮；
2. **击破记录** — 逐条记录 `# / 时刻 / 目标 / 反应ms / 判定`，**数据诚实**的落点；
3. **难度参数** — 当前档位实际生效的旋钮值，直接来自 `Difficulty`。

**顶部信息条的 HUD** 另画一份塌陷计（格子数 = `collapseLimit`）——"还剩几格"是
决定生死的量，不该逼玩家离开画面去看侧栏。

## 9. 验收标准

### 9.1 功能

- [x] 三种模式各能正常开局、出题、击破、结算
- [x] 同屏不出现重复目标（字母 / 单词 / 拼音三种都成立）
- [x] 单词/汉字模式的前缀匹配正确：中途打错 → 失误 +1、缓冲清空、进度回退
- [x] 非字母数字键（方向键、功能键、中文输入法的 `Process`）被忽略，不计失误
- [x] `ctrl/meta/alt` 组合键不触发游戏输入
- [x] 气球落地 → 本列沉 5px、邻列 2px、隔列 1px，坑呈碗形
- [x] 塌陷列数达 `collapseLimit` → 本轮结束、结算浮层出现
- [x] 结算数字全部来自 `state`，与侧栏一致
- [x] 评语按 `GRADE_HIGH` / `GRADE_MID` 双阈值判定
- [x] 「重开本轮」沿用当前模式与档位；「再来一轮」同理；菜单高亮与实际一致
- [x] 切换标签页 / 窗口失焦自动暂停，回来接着走
- [x] 菜单打开时键盘输入不进入游戏

### 9.2 像素

- [x] 逻辑分辨率恒为 256×240，`canvas.width/height` 与之相等
- [x] 显示缩放只取整数倍（1～4）
- [x] `imageSmoothingEnabled = false`，CSS `image-rendering: pixelated`
- [x] 渲染代码中**不出现任何硬编码色值**（全部来自 `readPalette()`）
- [x] 不用 `ctx.arc` / `ctx.ellipse` / `shadowBlur`
- [x] 5×7 字模用于所有 ASCII 显示；汉字走二值化点阵块

### 9.3 难度不虚标

- [x] L0 与 L9 的实测生成间隔 / 下落秒数与 `Difficulty.LEVELS` 一致
  （实测：L0 = 9.0s、L9 = 2.7s，与表完全相符）
- [x] 单词/汉字模式的下落时间随目标长度线性补偿
- [x] 菜单与侧栏展示的档位值 = `Difficulty.config()` 的返回值

### 9.4 数据诚实

- [x] 侧栏记录表的反应时间是当场测量值，无估算、无平滑
- [x] 「慢」的判定基准是**该气球自身**的可用时间，不是全局常数
- [x] 结算里的平均/最快反应直接来自 `log`，无筛选

### 9.5 工程

- [x] 无 `package.json`、无 `node_modules`、无构建步骤
- [x] 无图片 / 字体 / 音频文件
- [x] 无 CDN、无外部请求（除指向本项目仓库的两个链接）
- [x] **不新建测试文件**（系列约定 + 用户规约）；验证靠 `window.TypingGame`
      现场驱动
- [x] `python3 server.py` 可直接跑起来

## 10. 不做的事

- 不做 FC ROM / 模拟器方向（原版没有独立 ROM，且与"纯前端"定位冲突）；
- 不做五笔字根模式（用户未选）；
- 不引 Phaser / React / 打包器（与系列约定冲突）；
- 不引入任何图片、字体、音频文件（这是立项前提）；
- 不做联网排行 / 账号系统（零后端定位）。
